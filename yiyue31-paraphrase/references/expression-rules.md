# 表达差异规则（英→中改写）

> 本文件是**唯一源真相（single source of truth）**：既指导改写（analyze-prompt / generate-paraphrase-prompt 应用），也作验收清单（faithfulness 查 R0、translationese 查 L1、conciseness 查 L2）。SKILL.md 不重述此处规则；其余 prompt 只回指本文件。

把英文技术文章/新闻改写为地道、精简的中文。三层规则，ID 稳定，供 rule-confirm 逐条核对：

- **R0 转述身份**——**绝对不用**第一人称（我/我们）冒认原文作者，由 faithfulness 门验收。
- **L1 地道（R1–R8）**——消除照搬英语结构产生的翻译腔（含代词滥用），由 translationese 门验收。
- **L2 精简（R9–R11）**——砍废话、并同义、丢低价值，由 conciseness 门验收。

每条给「不好（照搬/冗余）→ 好（地道/精简）」对照。改写时照 R0–R11 执行；某条对本句不适用，在 rule-confirm 里标 N/A + 理由即可，但**不可整条删除**。

---

## 转述身份（R0）

### R0 绝对不用第一人称（我/我们）
改写是**转述别人的内容**——**"我/我们"是硬禁止，绝对不用**。源文里的"我/我们"是原文作者（或其团队）的第一人称，照搬会读成"改写者（博客作者）做过这些事"，构成冒认。改第三人称（他们 / 原文团队 / 具体名，如"Claude Code 团队"）或无人称。
- 不好：「我们删掉了 Claude Code 超过 80% 的系统提示词。」（读成博客作者删的）
- 好：「Claude Code 团队删掉了超过八成的系统提示词。」
- 不好：「我们称之为上下文工程。」「下面是我们学到的经验。」
- 好：「这被称为上下文工程。」「以下是他们总结的经验。」

**保留"你"**：源文里对着读者说的"你"（如"你的 CLAUDE.md""你组装上下文时"）是冲博客读者说话，保留，不改。

**金句例外**：`**中文（English）**` 金句是显式署名的引语（英文原文在场，归属明确），其中的第一人称可保留，不构成冒认。

## L1 地道（R1–R8）

### R1 关系从句 → 拆短句
英文用 who/which/that 串起来的定语，中文别堆成一个长"……的"修饰，拆成短句。
- 不好：「上季度部署的那个降低了延迟的系统已经上线了。」
- 好：「这套系统上季度上线，延迟降了不少。」

### R2 被动 → 主动
不必要的"被/受到"改成主动；动作承受者本就明确时尤其要改。
- 不好：「该 bug 在数小时内被团队修复了。」
- 好：「团队几小时就修好了这个 bug。」

### R3 名词化 → 动词化
英文爱用名词表达动作（the implementation of / a reduction in），中文用动词更顺。
- 不好：「缓存的实现导致了负载的降低。」
- 好：「上了缓存，负载就降下来了。」

### R4 长多从句 → 拆 2–3 短句
三个以上嵌套逻辑挤在一句，拆成 2–3 个短句，按时间或因果重排。
- 不好：「尽管最初面向已习惯旧界面的用户的推广遭遇了抵触，团队仍坚持并在引入引导教程后最终看到采用率攀升。」
- 好：「刚上线时，习惯旧界面的用户抵触很大。团队没退，加了引导教程之后，采用率才慢慢上来。」

### R5 强调句（it is X that…）→ 直陈
英文 cleft 强调结构，中文直接说，把被强调的成分放进自然语序。
- 不好：「正是数据质量决定了模型的性能。」
- 好：「数据质量决定模型性能。」

### R6 生硬连接词 → 删或自然衔接
therefore/however/furthermore/moreover 别逐个译成"因此/然而/此外/而且"串场；多数可删，或用"但/于是/而"自然带过。
- 不好：「因此，我们切换到了流式架构。然而，这引入了新的挑战。此外，……」
- 好：「我们换成了流式架构，但新的麻烦也跟着来了……」

### R7 "作者 + 言说动词" → 观点作主语
别让"作者认为/声称/指出"占主语位把观点隔远；把观点/概念/证据放主语。只在争议、直接引语或需区分归属时才署名。
- 不好：「作者认为，微调的作用被高估了。」
- 好：「微调的作用被高估了。」

### R8 滥用代词 → 省略，或用"他们"
中文是高语境语言，主语/宾语清楚时不用代词；英文强制出现代词（they/it/this/that），照搬就啰嗦、翻译腔。**能省则省**；需要指代原文作者/团队时用**"他们"**（首次可用具体名如"Claude Code 团队"点明），不要 他/它/这/那 反复指。
- 不好：「他们删掉了系统提示词，他们称之为上下文工程，他们把它放进了 claude doctor。」
- 好：「系统提示词删掉了大半，这套做法叫上下文工程，整理进了 claude doctor。」
- 不好：「这让 Claude 能处理复杂引用。它可以在 artifacts 里引用。」
- 好：「这让 Claude 能处理复杂引用，可直接在 artifacts 里引用。」

对着读者的"你"保留；R0 管"我们"（绝对禁），本条管其余代词。

## L2 精简（R9–R11）

### R9 删废话（复述 / 铺垫 / 客套 / 元叙述 / 过渡辞）
借鉴 yiyue31-prune 的废话判定：复述、过渡辞、装饰、空泛套话、元叙述（叙述"文章在讲什么"而非直接讲）一律删，直接进实质。
- 不好（开场铺垫 / 自我引用）：「我之前写过如何最好地提示 Claude 5 模型。」→ 压到半句或删。
- 不好（过渡辞）：「总的来说」「另外」「下面是我们学到的经验」「把这些汇总起来」「试试简化」→ 删，直接给内容。
- 不好（元叙述）：「这个问题随着 Claude 能力进化变得出奇地困难。」→ 空话，删或换成实质。

**判定法**（借自 prune）：删掉这句，读者会少知道一个观点或事实吗？不会 = 废话，删。

### R10 合并同义句
几句说的是同一件事，合并成一句；别逐句保留。
- 不好：「缓存有用。它通过存储结果加速。这意味着响应更快。」（三句一回事）
- 好：「缓存存下结果，响应就快了。」

### R11 丢低价值举例
纯罗列、不承载证据强度的举例砍掉；若举例本身是关键证据，保留并点明其证据作用。
- 不好：「许多公司都在用，比如 A 公司（2021）、B 公司（Q3）、C 公司（去年三月）。」
- 好：「不少公司都在用。」

## 判定优先级
冲突时按 SKILL.md 优先级轴：**核心信息保真 > 地道 > 精简 > 次要细节**。L2 精简不得扭曲保留的核心信息——宁可少砍，也不能把含义砍变样。
