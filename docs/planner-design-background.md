# yiyue31-planner 设计背景与教训

> 本文档记录 `yiyue31-planner` skill 的原始需求场景、设计决策的来由、演进中暴露的问题，以及从中提炼的教训。目的：**防止后续在设计同类 skill 时重复踩坑**。
>
> 性质：设计背景与决策记录（非实现规范）。

## 1. 原始需求场景

### planner 的目的
拿用户需求 → 产出一套结构化 YAML 任务计划（`task-list.yaml` + `tasks-NN.yaml`），供下游 `yiyue31-orchestrator` 逐任务执行。

### 触发设计的真实场景
作者把一个**需求文档**直接丢给 AI，让 AI 一次性产出完整执行计划，**结果卡住了**。

### 当初的归因
作者判断卡住的原因是**上下文超长**。

### 基于归因的设计决策
为应对"上下文超长"，设计了 **Generator + Reviewer 双子代理 + 最多 5 轮对抗评审** 的机制：Generator 子代理产出计划，Reviewer 子代理做对抗式质量评审，多轮迭代。

## 2. 设计的演进与暴露的问题

### 子代理机制引入后的问题
引入子代理后，出现**新的**可靠性问题（这些是子代理带来的，不一定是原始"卡住"问题的延续）：
- **无响应**：子代理长时间无返回，主循环空转。
- **无产出**：子代理跑完但产出为空/废 YAML 被丢弃。
- **主循环空转**：主模型在两轮之间不调子代理，自我循环。

### 为解决问题尝试的方案膨胀
为治理上述问题，逐步堆叠了"三层防御"（预判 / 预防 / 补救）：输出契约写死、分阶段产出、PostToolUse hook 校验、`BASH_MAX_OUTPUT_MS` 超时、重试计数器、硬熔断、主循环心跳、Reviewer 滥用 PASS 反制……涉及提示词重构 + hook 脚本 + settings.json + env var + 计数器。

### 复杂度失控
方案膨胀到**偏离 skill 提示词的合理形态**，变成一个系统工程。结论：复杂度已不可控，决定换思路。

## 3. 关键反思（多为未决，判据待验证）

### 反思 A：原始归因存疑，可能从一开始就错了
"卡住"被归因为"上下文超长"，但这个归因**从未被验证**。真实原因可能是：
- **输出超长**（计划太大被截断）——解法是分阶段产出，不需要子代理。
- **任务太复杂**（不知道怎么拆）——解法是更好的需求分解，不需要对抗评审。
- **需求模糊**（该不该猜）——解法是澄清机制，不需要子代理。
- **模型能力上限**——缩小单次范围。

关键矛盾：即便真是"输入上下文超长"，**Generator 子代理的 prompt 照样要塞进整个需求文档 + 格式规则**，并没对症。**子代理拆的是产出端，不是输入端**——可能从未解决原始问题。

### 反思 B：子代理可能净负债
为解决问题 A（卡住）引入子代理，结果子代理带来了问题 B（空转）。治理 B 的方案又让 skill 无限膨胀。**A 可能根本没被解决，B 却是新增的**。

### 反思 C：planner 与 orchestrator 结构对称，但只有后者用对了
两个 skill 是同一模板的两个实例（主代理 + Generator + 评审子代理 + 多轮 + 相同状态字段）。但：
- **orchestrator 处理客观可验证任务**（代码能跑、测试过不过）——评审有确定性判据，多轮重试有意义。复杂结构**有真实价值**。
- **planner 处理主观质量判断**（计划够不够好）——Reviewer 对抗评审是主观的、可滥用的，多轮没有确定性终止判据。**把为客观任务设计的机制套到主观判断上，必然膨胀且不可控**。

### 反思 D：planner 的对抗评审可能是冗余
orchestrator 的执行本身就是计划最强的评审（任务失败/依赖断裂/criteria 不满足会立刻暴露），且有 Plan Issues 机制反馈计划缺陷。planner 自带对抗评审可能是冗余的一道关。

## 4. 教训（防止后续再犯）

> 这部分是本文档的核心价值——跨 skill 可复用的方法论。

1. **遇到 AI 行为异常，先验证根因归因，再设计机制。** 不要基于未经验证的假设（如"上下文超长"）去设计复杂机制。归因错了，后续所有设计都建立在错误前提上。**"卡住"的真实原因（不响应/截断/质量差/纠结）决定完全不同的解法**——先搞清楚现象，再归因。

2. **复杂度必须匹配载体形态。** skill 是提示词，把系统工程（hook + env + 计数器 + 熔断）压进提示词必然失控。当方案膨胀到超出载体，停下来重审目标，而非继续堆机制。

3. **子代理是可靠性负债，慎用。** 每引入一个子代理，就引入"无响应/无产出/空转"的风险和一整套治理成本。只有当子代理带来的收益（如客观可验证的分而治之）明确超过这笔负债时才用。

4. **对抗评审/多轮迭代只适用于客观可验证场景。** 主观质量判断（"计划好不好"）没有确定性判据，对抗评审会退化为可滥用的走过场。客观任务（"代码对不对"）才适合多轮重试。

5. **判断一个机制是否"确定性"，追问"触发它的到底是谁"。** 是 harness（env var、hook 事件 → 确定性强制）还是模型（提示词指导 → best-effort）。凡是听起来"不依赖模型"的机制，都要追问这一句——本次任务中"hook 确定性重写""Workflow schema""hook 状态自检"三次被这一问击穿。

6. **优先找 harness 级原语，而非在提示词层堆机制。** 最朴素、零配置的 harness 级机制（如 `BASH_MAX_OUTPUT_MS`）往往比提示词层堆叠的方案更可靠、更简单，却最容易被忽略。

7. **大规模产出要在入口拦截，不要试图一次性处理。** 规模估算：一个完整任务项约 15 行 YAML、300-500 字符，**200 个任务 ≈ 40k-80k tokens（仅产出）**，必然超出模型单次输出上限（典型 8k-32k tokens）→ 截断；而多轮对抗评审会让大计划在 context 里反复累积 → 溢出。**解法不是让 planner 更聪明地处理大规模，而是让 planner 拒绝一次性大规模**：入口预估任务数，超阈值（如 15）就**强制分阶段**，每次只产一个阶段（≤15 任务、≤8KB），阶段间靠文件交接不累积。分阶段必须从"建议性"升级为"硬门槛"——用户想一次性产 200 任务时，明确拒绝并要求分阶段。子代理设计（要求一次性产完整文档集）天然阻碍分阶段，应砍掉改为主 agent 直接产。

8. **read-only 调查任务是 context 溢出的首要风险，必须特殊对待。** 调查任务（`code-review [read-only]`，读代码产分析报告）输入 ≫ 输出，远比实现任务（输入 ≈ 输出）容易撑爆执行者 context。真实案例：旧 planner 处理单元测试报告时，产出一个 `T-investigate-managers`——读 `manager/*.java`（30 个类）+ 多个包 + 测试，8 类问题全覆盖，被 19 个修复任务依赖（"漏斗"结构），执行时第一个任务就报"Generator subagent hit a context limit"。三条对策（已落进 planner v0.4.0）：① **constraints 禁止整包通配**（`*.java`），必须列具体文件或"先 grep 筛选再读命中子集"；② **read-only 任务输入上限约 8 文件**，超了拆成子调查 + 汇总（汇总只读子文档不读源码）；③ **禁止调查漏斗**——不产"一个大 read-only 调查全部任务被众多修复任务依赖"，改为把源码读取分散进每个修复任务的 constraints（局部调查）。**根因**：旧 planner 的对抗评审维度（完整性/失败模式/边界）鼓励"全貌调查"，加上无读取规模约束，于是产出这种读爆任务。新 planner 通过砍维度 + 这三条规则从源头阻止。

9. **瘦身提示词时，"why"（目的/意图）不是噪音，必须区分对待。** 本次 planner 瘦身曾犯一个错：跟着"why 都是给人看的设计噪音"的判断，删了几处 why。后被纠正——**why 让模型理解意图，从而在规则没明确覆盖的边缘情况下仍能做出符合意图的选择**，是让规则泛化的载体。正确区分两类：**目标 why**（陈述某规则/步骤要达成什么目的，删了模型会在边缘情况违背意图）→ 必须保留；**动机 why**（解释历史设计选择，模型照做即可）→ 可删。判别标准：模型不知道这个 why，会在边缘情况做错吗？会→留。本次已恢复 planner 的两个目标 why（Step 1 强制检查点的 why、Step 2 分阶段阈值的 why），并把这条规则写入项目 `CLAUDE.md`。**教训**：提示词精简要砍的是"动机/重复/啰嗦"，不是"意图"——砍意图等于砍掉模型在边缘情况对齐目标的能力。

## 5. 结局

上述反思已在 v0.4.0 落地：planner 改为线性流程，**移除 Generator/Reviewer 子代理与对抗评审**，改为直接产出 + 静态自校验（completeness / actionability / dependency + 格式），并加入规模门槛强制分阶段与 read-only 调查的读取约束（见教训 7、8）。反思 A–D 的判断（子代理净负债、对抗评审不适配主观判断、机制冗余）被采纳。
