# translator 双语输出设计讨论（2026-09-18）

> 参与方：Yiyue31（用户）+ Claude（分析）。
> 用户输入的逐字存档：[yiyue31-translator-bilingual-discussion-user-inputs.md](./yiyue31-translator-bilingual-discussion-user-inputs.md)（原状存档，禁止修改；本文件中对用户输入仅作摘录）。
> 议题演化：translator 家族是否增加中英对照输出 → 派生方向与对齐方案 → 功能归位（yiyue31-translator 去大文档、yiyue31-xl-translator 落地双语输出）。

---

## 第 1 轮：是否有必要增加中英对照输出

**用户**（摘录）：是否有必要增加中英文对照的输出。可以选择纯中文，也可以选择中英文（一段中文，一段英文，中文在上，英文在下）。先分析。

**分析结论**：

- **定性**：双语对照不是必要功能，是可选交付格式。现有管线的目标是产出高质量纯中文译文，该目标不因缺少双语输出而受损。
- **价值**：① 英语学习精读（段落对照是精读常见载体）；② 核对与引用便利。反向论点：现有注释体系已是"局部对照"（词级 `中文（English）`、金句句级、`[KEEP]` 术语），且 `original-{title}.md` 本就存档在旁，缺的只是排版对齐这一层。
- **代价**：① 段落对齐脆弱（意译允许重构句式，块级 1:1 无保证）；② 与注释体系的张力（双语版里英文原文就在下方，词级括注价值被稀释）；③ 当时识别的下游 refined-stock 命名约束（后续第 2 轮用户裁定无需考虑）；④ 审校步骤读纯中文，对照输出必须在纯中文定稿之后派生。
- **方案雏形**：`--bilingual` 可选参数（与 `--literal` 同构），定稿之后派生第三文件，主管线不动。

## 第 2 轮：程序合并与锚点；派生方向

**用户**（摘录）：无需考虑 refined-stock；支持两种输出模式（纯中文保持现状、中英文为新增）；中英文模式可否程序合并、只加锚点；或反向思路——默认双语程序出纯中文 / 默认纯中文程序出双语。先分析。

**分析结论**：

**① 程序合并可行，且锚点大部分现成，不必新造**：

- chunk 级配对 by construction 精确（manifest 直接给定）；
- 标题是强锚点（翻译规则保格式，标题级别+顺序两侧 1:1）；
- 代码块是指纹锚点（机械校验已强制字节一致），URL/图片同理；
- 算法：chunk 配对（精确）→ 节切分（标题锚点）→ 节内块按序配对 + 指纹校核（启发式）→ 块数不匹配的节降级为节级对照，降级清单随脚本输出可见。

**② 注入人工锚点（如 `<!-- b7 -->`）是升级方案而非首发**：锚点须由翻译 subagent 原样搬运才能存活，意味着翻译提示词加规则、机械校验加硬判、失败打回重译增加返工；锚点会渗入审校输入与扫描对象；两种模式造成管线行为分叉。首发用结构匹配，跑若干篇统计降级率，确实高了再上锚点。

**③ 派生方向只能是"纯中文为源、程序派生双语"，不能反向**：

- 管线的翻译单元和审校单元都是纯中文 chunk；双语只能由"原文 chunk + 译 chunk"机械交错产生（让 subagent 输出双份是纯浪费且污染审校）；
- "默认双语、程序 strip 出纯中文"是无意义绕路：依赖链永远是 zh → 双语，strip 之前纯中文本来就已存在；
- 质量链条论据：Steps 5-9 认证的是纯中文文本，纯中文是被审校过的规范产物，双语是其确定性投影（认证可传递）；反向则出处关系倒置，无机械收益；
- "默认双语"唯一合理形态是展示层默认：`--bilingual` 先 opt-in，使用频率证实后再翻默认。

## 第 3 轮：记录存档 + 功能归位

**用户**（摘录）：① 把本次沟通记录到文档，用户输入单独成档、原状不可修改；② 大文档翻译已在 yiyue31-xl-translator 实现，yiyue31-translator 的大文档功能要去掉；yiyue31-xl-translator 也要实现双语输出。先分析。

**分析与结论**（本轮要点，完整分析见当轮会话回复）：

**A. yiyue31-translator 移除大文档（多 chunk）路径**：

- 删除：Step 1.5 分段 + `scripts/doc_segmenter/` 整目录（bun 依赖随之消失）、`chunks/`/`translated-chunks/`/manifest/progress 脚手架、Step 11 全局一致性 + `consistency-checklist.js`（其存在理由就是分块）、README 中"全局一致性不读整篇"等设计决策条目。
- 收缩：每 chunk 派发 → 全文单次（审校"维度不合并"纪律保留）；`verify-pipeline.js` 的 chunk 完备性矩阵适配单文件形态（保留反伪造骨架：报告存在性/合规表/SKIPPED 披露）；`verify-mechanical.js` 本身不改（本来就吃两个路径，改调用方式）。
- 保留不变：两阶段注释、四维审校、terms.md 维护、共享评估 prompts。
- 路由：>40KB 改为提示改用 xl-translator（或对称自动交接，xl Step 0 已有反向先例）——待决。
- ≤40KB 行为等价（原本就走单 chunk subagent）。

**B. yiyue31-xl-translator 落地双语输出**：

- 落点：final-gate PASS 之后派生（尊重"Step 10 = 流程真正的最后一个动作"）；新脚本 `derive-bilingual.mjs` + 动词表新增（如 `双语对照 <title>`）；brief 字段后续可选。
- xl 侧现成锚点更强：chunk 配对精确（manifest+sha）；**标题双语锚是内建锚点系统**（brief 默认开：标题行纯中文 + 次行 `*English Heading*` 逐字，标题级对齐免费获得）；代码块指纹（verify-mech 硬判保真）；落盘即 LF 归一。
- 命名：`translated-<title>-bilingual.md`——不以 `-zh.md` 结尾、无发布前缀；但红线③"唯一交付物"表述需微调（双语版定位为派生视图而非第二交付物）——待决。
- 兼容待核：final-gate 对工作目录根多出文件的容忍度（术语统一轻命令后重入场景）；status.mjs 是否上报该文件。
- 双语版中标题锚行 `*English Heading*` 建议保留（派生脚本只交错不改块内容）——待决（次要）。
- 测试按家族惯例 unit + regression；导出纯函数 interleave（仿 merge.mjs assemble 被 final-gate 复用的先例）。

**C. 两 skill 关系定稿**：translator = ≤40KB 轻量线，xl = >40KB 重线，双向路由；双语功能两边各自实现（家族自包含惯例，零跨 skill 运行时依赖），translator 侧更简单（无 chunk 层）。

## 第 4 轮：待决与待核逐项展开

**用户**（摘录）：待决项与待核项列出建议和原因，说详细点；实施序（先 xl 双语、后 translator 瘦身）同意，先记录到文档。

**建议方案（待用户拍板）**：

1. **translator >40KB 路由 → 建议：提示+停止。** 检测到 >40KB 时回复一行"本文 XX KB 超 40KB，本 skill 不再处理大文档，请对同一输入改说『翻译大文档』（yiyue31-xl-translator）"并停止，不落任何文件（大小检查置于建目录/落盘之前）。原因：① 自动交接要求 translator 会话中途采纳 xl 的全部执行模型（工作目录约定、status/续跑机制、会话预算），上下文成本高且易错；② 反向降级出口缺失——xl 交接到 translator 读不到 SKILL 时可自行单 chunk 跑完，translator 交接到 xl 失败时只能停止询问（chunk 路径已删），自动交接只覆盖快乐路径；③ 频率与成本不对称——xl Step 0 已自动路由小文章，反向场景仅"用户直接对 translator 发大文档"，代价是多说一句话；④ 角色不对称——xl 是编排型 skill，向下路由自然；translator 是轻量线性 skill，中途启动状态机不自然。
2. **红线③措辞 → 建议：交付物/派生视图二分。** 现行"唯一交付物 translated-<title>-zh.md 由终检 PASS 原子改名产生"与双语文并存会自我矛盾。修订口径：`translated-<title>-zh.md` 仍是唯一交付物；`translated-<title>-bilingual.md` 定位为 PASS 后由交付物+原文机械派生的**只读视图**——非交付物、不经终检、sha 不锚、不受手修保护、可随时幂等重生成，命名永不以 `-zh.md` 结尾。原因：这份区分回答了所有后续问题（终检不管它、改坏重生成就行），且不增加任何认证负担；若当作第二交付物则要为它设计 gate 覆盖与 sha 锚，纯增成本无收益。
3. **双语入口形态 → 建议：动词 + brief 字段组合（flag 只是写 brief 的入口动作）。** ① brief 新增字段 `双语对照: 关`（Step 0 落盘，用户发起时表达过双语意向即写 开）；② PASS 后主 agent 查 brief：开 → 跑 derive 脚本；③ 动词表新增 `双语对照 <title>`：交付后任何时候可说，生成或幂等重生成，兼容"先交付后要双语"的存量项目。原因：xl 纪律一"状态只从文件系统推导"——跨会话续跑时首条消息里的 flag 意图必然丢失，必须落盘进 brief；纯 flag 方案在 resume 场景失效，纯动词方案无法在发起时表达意向，两者互补。translator 侧无 brief/续跑机制，简化为：发起时说了就交付后跑脚本，或交付后随时补跑，SKILL.md 记两句话。
4. **final-gate 容忍度 → 建议核验法：先 grep 后回归测试钉住。** 实现前 grep final-gate.mjs 的根目录文件枚举/重入前置条件；实现时加回归 fixture"工作目录含 bilingual 文件 → final-gate 判定不变"。原因：现有证据（final-gate.mjs:487 只扫 translated-chunks/chunks/adjudications/reviews 子目录）指向无冲突，但"终检重执行一切"的哲学要求以测试钉死而非以推断放行；风险场景是术语统一轻命令触发的终检重入。
5. **segment/ 解析器复用 → 决策规则：能 import 就复用，需重构就独立写。** 若 segment/ 已导出 fence 感知、段落粒度的块解析函数 → import 复用；若复用需移动 segment.mjs 内部代码 → 在 derive-bilingual.mjs 内独立写（约百行）。原因：segment 的解析为切 chunk 服务（标题树+目标带），derive 要的是严格块序列（配对用），粒度本就不同；且动 segment/ 的重构会波及"拼接 sha === 原文 sha"这一最承重的关卡，为 DRY 冒_sha 门回归风险不值。

**定案（2026-09-18 用户同意）**：

- **实施序**：先做 yiyue31-xl-translator 双语输出（独立增量，不碰承重墙），后做 yiyue31-translator 大文档路径移除（删除面大，独立提交）。

## 第 5 轮：旧交付物兼容与"交付/翻译解耦"确认

**用户**（摘录）：① 原来交付的最终文档是否影响此次修改；② 可否把交付与翻译解耦——纯中文/中英文都是最终交付的选择，不应影响翻译。

**结论**：

1. **双向不影响**。此次修改全部为增量（新脚本/动词/措辞修订），不触碰任何已存在文件；派生脚本只读交付物与原文、幂等可重生成。反向：任何"有交付物 + 有原文"的存量 workdir 都可追溯生成双语版（动词直接跑）——这是解耦设计的红利。两处边角：① translator 瘦身后，旧"进行中"的多 chunk 工程无法被新 SKILL 续跑——不写迁移逻辑，遇旧结构披露并给出口（git 历史版本跑完 or 重新发起；已产出交付物的项目本已完结，不受影响）；② xl 交付物被手改（sha 与 REPORT 锚不符）时派生照跑，附 WARN 一行。
2. **解耦正是现行设计**。翻译管线（含注释密度、风格等全部翻译行为）与输出格式选择完全正交；双语版 = f（PASS 后交付物, 原文）。此前讨论中"双语版里词级括注冗余"的张力，明确选择**不放宽注释政策**，就是为了守住这条正交性（宁可注释冗余，不让输出格式反向影响翻译）。brief 字段定位为**交付配置**（为 resume 保真而落盘），非翻译参数；若要更彻底可退化为纯动词方案，代价是跨会话续跑丢失发起时意向、需交付后补说。动词 `双语对照 <title>` 即解耦终态：流程全部结束后任意时刻可补生成。

## 第 6 轮：双交付并存确认 + 拍板项重述

**用户**（摘录）：① 是否支持同时生成两个交付物（纯中文 + 中英对照）；② 再描述一下需要拍板的内容。

**结论**：

1. **支持并存**。brief 双语对照=开（或动词触发）时，PASS 后 zh 交付物与 bilingual 派生视图并存于同一工作目录，一次拿到两个文件。形式上仍是"一个交付物 + 一个派生视图"（红线③二分），zh 永远是管线产物、双语版永远是附加——不存在"只有双语版没有纯中文版"的组合。
2. 待拍板三项重述给用户：路由形态（A 提示+停止 / B 自动交接，建议 A）、双语文件身份（交付物/派生视图二分，建议二分）、入口形态（动词+brief 交付配置 / 纯动词，建议组合）。

## 第 7 轮：全案拍板 + HANDOFF

**用户**（摘录）：全部采用建议；确认是否还有待讨论项；无则记录 HANDOFF 文档（换机+冷启动）。

**结论**：

1. 三项拍板全部采纳：① translator >40KB 路由 = 提示+停止；② 双语文件身份 = 交付物/派生视图二分；③ 入口 = 动词 + brief 交付配置组合。
2. 设计定稿，**无剩余待讨论项**——两个待核点（final-gate 容忍、segment 解析器复用）属实施时验证动作，已编入执行序前置核验。

## 结论汇总（截至第 8 轮）

1. 纯中文 `translated-<title>-zh.md` 永远是规范交付物；双语版是定稿后机械派生的视图，零边际 LLM 成本。
2. 派生方向不可逆：zh → 双语（依赖链与认证链共同决定）。
3. 对齐策略：结构匹配首发（chunk 配对 / 标题锚 / 代码指纹 + 节级降级 + 降级清单），人工锚点仅作数据证明不足后的升级方案。
4. 双语文件命名避开 `-zh.md` 后缀。
5. 大文档能力归 xl-translator：translator 移除多 chunk 路径；双语输出两个 skill 各自实现。
6. **交付与翻译解耦（设计不变量）**：输出格式（纯中文/双语）是 PASS 后的交付选择，翻译行为与之正交——翻译管线对输出格式零感知。
