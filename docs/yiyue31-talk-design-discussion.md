## 一、分析前提：当前 skill 的关键现状

便于对照，先固定几条基线事实。

- **定位**: 通过交互式讨论生成"用户观点文档"，记录用户对文章的理解、观点和收获。产出面向用户本人（心得），不面向外部读者。
- **Step 4（交互式讨论）现状**:

## 二、用户想法与分析

### 想法 1：是否为每个问题提供 3-5 种回答或关键字？

> **用户原话**: 要提供每个问题的3~5中回答，或者简单的关键字？这样可以引导用户，但是会导致用户不再深入思考。

**理解**: 针对 Step 4 的"引导问题"，是否附带候选答案或关键字，以引导用户作答。用户已意识到引导性与思考深度之间的张力。

**分析**:
- 现状已显式选择"自由文本对话，不用预设选项"，目的正是避免选项限制深度。用户的担忧与现状设计意图一致。
- 三种做法及权衡:
  1. **维持全开放（现状）**: 深度最好，但用户卡壳时无抓手。
  2. **前置给出候选答案/关键字**: 引导性强，但易诱导、收窄思考，违背"不用预设选项"的 why。
  3. **折中**: 关键字作为"切入角度提示"，仅在用户犹豫或主动求助时给出，并明确标注"仅供参考，鼓励自由作答"。保留 why（默认开放），增加抓手。
- 倾向: 折中（做法 3）。但需用户确认对"深度 vs. 抓手"的偏好。

**涉及步骤**: Step 4 引导问题设计。

### 想法 2：记录用户原始输入 + AI 简要反馈

> **用户原话**: 记录用户的原始输入和AI的简要反馈。

**理解**: 在讨论记录中，除"用户原话"外，也明确记录 AI 对用户输入的即时反馈（态度/补充/挑战的理由），而不只是结尾的"AI 总结"。

**分析**:
- 现记录格式含 AI 引导、AI 总结、追问，但缺一个"AI 对用户这段话的即时反应"槽位。
- 这是低风险、明确的记录格式增强。
- 同时支撑想法 3 的"访谈记录"形态: 访谈记录天然包含采访者反应。

**涉及步骤**: Step 4 记录格式。

### 想法 3：通过访谈/采访形成摘要稿、新闻稿或推荐稿

> **用户原话**: 通过访谈或采访的方式形成摘要稿或新闻稿或推荐搞。

**理解**: 两层含义。
- (a) **方法**: 把讨论重构为"访谈/采访"（结构化问答）。
- (b) **输出**: 产出 摘要稿 / 新闻稿 / 推荐稿（面向读者的成品），而非当前的"用户观点文档"（面向本人）。

**分析**:
- (a) 与想法 4 强相关: 把讨论入口从"话题"转为对"具体观点"的追问。
- (b) 是方向性变化。当前 skill 的 why 是"记录用户本人的理解与收获"；新闻稿/推荐稿的 why 是"面向读者呈现内容"，受众与目的不同。
- 三种落地路径:
  1. **替换**: 用新输出形态取代当前"用户观点文档"。风险: 改变 skill 定位，且与现有 yiyue31-summary（摘要）重叠。
  2. **并存**: 在 Step 5/7 增加输出形态选项（心得稿 / 摘要稿 / 新闻稿 / 推荐稿）。灵活，但复杂度上升，多种体裁的生成规则都要维护。
  3. **拆分**: 新闻稿/推荐稿做成独立 skill，本 skill 保留心得定位。边界清晰，但要维护多 skill。
- 依赖提示（仅提示不处理）: "摘要稿"与仓库已有 yiyue31-summary skill 功能重叠，需避免重复造轮子。

**涉及步骤**: Step 5、Step 7（若采纳）；可能触发新 skill。

**待澄清（四个想法里最关键）**: 用户希望走哪条路径？

## 六、后续沟通追加

### 2026-07-21 第二轮：目的澄清 + 访谈 vs 讨论

**用户目的（原话归纳）**: 读到好的技术文章或新闻时，想把"我的"心得和认识分享出来；倾向用与 AI 访谈或讨论的方式；让我分析访谈还是讨论更合适。

**对想法 3 的收窄**: 输出应锚定"心得稿/评论稿"，而非新闻稿/摘要稿。理由: 新闻稿报道原文、摘要稿复述原文，都不承载用户声音；只有心得稿/评论稿（及勉强算的推荐稿）承载"我的"判断。上一轮想法 3 列的"摘要稿/新闻稿/推荐稿"中，摘要、新闻两项与目的不符，应剔除。

**访谈 vs 讨论的本质差异**: 角色是否对称。
- 访谈: AI 主导议程（备问、顺序、深浅、切换），用户主导回答内容。
- 讨论: 双方对等，谁都能抛话题、质疑、改方向。

**三维度权衡**:
- 原文覆盖度: 访谈高（按清单逐点追问），讨论不均匀（跟兴趣走易漏）。
- 心得深度: 访谈靠施压逼出 articulation，讨论靠共建、取决于用户发力。
- 声音归属: 讨论强，访谈弱（框架是 AI 的，易读成回应 AI 议程）。

**决定性判据**:
1. 心得是否已成形: 模糊感受 → 访谈更好（抽取 + 低负担 + 全覆盖）；已成形判断要找对手打磨 → 讨论更好。
2. 原文类型: 新闻偏反应式，访谈易引出；技术文若有技术异议要展开，讨论更对等。

**推荐结论**: 访谈为骨架、讨论为血肉，产出心得稿。
- 访谈骨架保证原文覆盖、降低用户组织负担。
- 两条护栏保声音: 问题锚定原文自身观点（接想法 4），AI 只探查不下结论；产出心得稿而非访谈录，记录作可选附录。
- 每个观点展开轮次允许讨论式交锋，留深度空间。

**反向条件**: 若用户主要读技术文、且带着明确技术判断去读、目的是找人辩论，则纯讨论更合适。

**对前述想法的副作用（选访谈后的收敛）**:
- 想法 4 → 成为采访者备问依据。
- 想法 1 → 张力消解: 访谈问题已足够尖锐，不再需要候选答案。
- 想法 2 → AI 追问/质疑本就是内容主体，自然进记录。

**仍未定**:
- 用户是否认可"访谈为骨架 + 讨论为血肉 + 心得稿输出"的整体方向。
- 若认可，再回到第四节逐项拍板（此时想法 1 已基本消解、想法 3 已收窄为心得稿）。
- references/ 与 README 的既有漂移仍未处理。

### 2026-07-21 第三轮：访谈被否，转向"策展式批注分享"

**用户反馈（原话归纳）**: 访谈形式太累，全程都是用户回答问题、耗时且疲劳。想要相对快捷的方式：把自认为的重点部分写出来，在部分地方加入自己的理解，最终分享出去。

**累的根因诊断**: 访谈累在用户处于"被动答题"模式，没有主导输出。解法不是换问法，而是翻转模式：用户回到作者模式（选材 + 批注），AI 退到辅助位（提取候选、排版、组装），不再盘问。操作量从"答几十问"降到"挑几个重点 + 写几句注"。

**与现有 skill 的边界确认**（已读 yiyue31-summary、yiyue31-merge）:
- yiyue31-summary: 替读者总结原文，无用户声音。
- yiyue31-talk（现状）: 重交互讨论，即疲劳来源。
- yiyue31-merge: 合并 summary + talk 产物，依赖前置。
- 用户要的是第四种"摘录 + 批注 → 分享"，目前无 skill 覆盖，是真实空缺。

**建议的轻量流程（草案）**:
1. 输入转 markdown（同现状 Step 1）。
2. AI 提取候选重点（复用 Step 2 分析，单遍，不多轮、不盘问）。
3. 用户多选保留/丢弃，可手动补加 AI 漏的。
4. 用户 selective 加批注（仅在有话处）；AI 不主动问，卡壳时可代拟由用户改。
5. AI 组装可分享 markdown（摘录 + 批注）。

**对现状 skill 的影响（改动较大）**:
- Step 4（交互讨论）→ 删除或可选。
- Step 6（观点映射）、Step 7（观点文档生成）→ 被"挑选 + 批注 + 组装"取代。
- Step 2 分析 → 保留，用途改为喂候选重点；建议去多轮审查。
- subagent 审查 → 大幅精简，用户为质量门。
- 本质: talk 从"讨论式观点提取"重写为"策展式批注分享"。

**待用户定的关键点**:
1. 第 2 步: AI 预提取候选（用户挑）/ 用户直接指段（AI 不预提取）。倾向前者。
2. 批注: AI 可否在卡壳时代拟（用户审改）/ 严格只记用户原话。
3. 输出: 纯摘录+批注 / 再加用户总结或推荐语。
4. 审查: 完全去掉一次成稿 / 保留一道轻量检查。

**仍未定**: 上述四点 + references/ 与 README 漂移。

### 2026-07-21 第四轮：点 vs 问题，收敛机制

**用户反馈（原话归纳）**:
- 访谈时 AI 经常问奇怪的问题，跟用户想法大相径庭。
- 想要快速收敛，在某几个自己认为好的"问题点"上收敛。

**病灶诊断**: 两条同源。AI 生成"问题"是猜的，常与用户不在一个频道；用户要的"快速收敛"是不被 AI 牵着发问，而在自己认可的几个点上集中。

**关键重构（点 vs 问题）**: AI 呈现**原文的点**（论断/亮点/争议点），不生成"问题"。用户从这些点里挑几个好的，只在挑中的点上加理解。选择阶段无任何 AI 提问，"奇怪的问题"从源头消失。

**收敛机制（具体）**:
1. AI 按章节抽"点"（关键论断 + 出彩句 + 争议点），每章 2-3 条、总数 ≤ 10。直接复用现状 Step 2 已算的"讨论价值等级"，高价值优先。
2. 用户多选保留，可补 AI 漏的。一次多选即收敛，秒级。
3. 只在保留点写"我的理解"（一两句），可选展开，否则留摘录。
4. AI 组装分享稿。

**对前述待定的影响**: 第 1 点（提取方式）已定——AI 预提取，但提的是"原文点"非"问题"，收敛权在用户。剩余 2/3/4（批注代拟、输出是否加总结语、是否保留审查）仍待定。

**仍未定**: 批注代拟策略 / 输出形态 / 审查去留 + references 与 README 漂移。

### 2026-07-21 第五轮：新增 dump 模式（一次性输入 → AI 整合成文）

**用户反馈（原话归纳）**:
- 访谈时 AI 问奇怪问题（第四轮已处理）。
- 想快速收敛（第四轮已处理）。
- **新增**: 也可一次性把自己的看法输入，AI 负责整合后成文。

**新模式定义（dump）**: 用户一次性写完所有看法（自由文本、可乱序），AI 读用户输入 + 原文，整理成可分享成稿。比策展更省力。

**两模式与用户状态的对应**:
- 心得已成形 → dump 模式（最快）。
- 心得未成形/模糊 → 策展模式（AI 提原文点，用户挑）。
- 开头一问路由: "你已经想好要说什么了吗？"想好走 dump，没想好走策展。极端简化可只留 dump。

**dump 模式关键护栏**: AI 只整理用户说过的话 + 必要原文上下文，不发明心得。用户说得少则成稿短，禁止为丰满而编造用户未表达的观点。与现状 skill"区分原文与我的观点、不编数据"一脉。

**dump 模式工作流（草案）**:
1. 文章转 markdown。
2. 用户一次性写所有看法（自由文本）。
3. AI 整合成稿（归并、标清原文/我的话、补上下文、顺可读性）。
4. 可选: AI 提示用户漏掉的原文点（内容锚定，非猜问题）。
5. 输出心得稿。

**对前述待定项的影响**:
- 第 2 项（批注 AI 代拟）: 看模式——dump 接受 AI 大幅整合，策展只记用户原话。
- 第 4 项（审查）: 看模式——dump 需一道 faithfulness 检查（防编造），策展不需要。

**当前剩余决策**:
1. 两模式并存（+ 一问路由）/ 只留 dump 单模式。
2. 输出形态（两模式共用）: 纯心得 / 加总结或推荐语。
3. references 与 README 漂移待清理。

## 七、完整新流程设计稿（待审）

> 本节按前八轮讨论综合而成，供逐节审阅。确认后据此重写 SKILL.md / README，并清理 references/。

### 7.0 定位（重写）

读到好文章（技术/新闻）后，快速产出**可分享的"我的心得"成品**。AI 不盘问、不替用户下判断，只呈现原文内容、整理用户的话。两条路径，开头一问路由。放弃原访谈/讨论式（累、跑题）。

### 7.1 共用前置

**Step 0: 输入格式化**
- 来源: URL（优先本地 skill 下载）/ 文件 / 粘贴。转 markdown。
- title 安全化（沿用现状规则）。
- 保存: `{title}/takeaways/raw-{title}.md`

**路由（Step 0 后）**
- 始终 AskUserQuestion: "你已经想好要说什么了吗？"
  - 想好 → **dump 模式**
  - 没想好 → **策展模式**
- 不自动跳过: 即使用户触发语已带看法，也由用户实时选（不预设）。

### 7.2 dump 模式（心得已成形）

**D1: 用户一次性输入看法**
- 用户自由写下所有看法（可乱序、可口语）。原样保存: `{title}/takeaways/user-dump-{title}.md`

**D2: AI 整合成稿**
- 读 user-dump + raw，产出结构化初稿:
  - 按主题或原文章节归并用户观点。
  - 明确标注原文 vs 我的话。
  - 补足让没读过原文的读者也能看懂的上下文（仅必要）。
  - 顺可读性。
- **护栏（强化）**: 严格按"原文 + 用户输入"成稿，禁止 AI 自行发挥。可重组、补必要原文上下文、顺可读性，但不得添加原文与用户输入之外的任何观点、论据或修饰。用户说得少，稿子就短。
- 保存: `{title}/takeaways/integrated-draft-{title}.md`

**D3: 缺口提示（可选）**
- AI 列出原文里用户没提到的关键点（"你没提 X、Y，要补吗？"）。内容锚定，非猜问题。
- 用户决定补/不补；补则并入 D2。

**D4: faithfulness 检查（本模式审查之一，轻量）**
- subagent 核对 integrated-draft: (1) 每条"我的"观点都能在 user-dump 找到来源；(2) 无原文与用户输入之外的内容（禁止 AI 发挥）。
- 不通过 → 按报告修正，最多 2 轮。报告: `{title}/takeaways/review-faithfulness-{title}.md`
- 用 Evaluate Once 模式 + 内联 criteria，不依赖外部文件。

**→ 进入 7.4 组装。**

### 7.3 策展模式（心得未成形）

**C1: AI 提取原文点**
- 单遍分析原文，抽取"点": 关键论断 + 出彩句 + 争议点。总数 ≤ 10，按讨论价值排序（高优先）。不做多轮 generate-evaluate。
- 保存: `{title}/takeaways/article-points-{title}.md`

**C2: 用户多选收敛**
- AskUserQuestion 多选: 哪些点保留。用户可补 AI 漏的。一次完成即收敛。
- 记录: `{title}/takeaways/selected-points-{title}.md`

**C3: 用户选择性加批注**
- 仅在保留点上写"我的理解"（1-2 句）。想写的写，不想写的留摘录。
- AI 不主动提问；用户卡壳时可要求 AI 代拟一句、再改。
- 保存: `{title}/takeaways/annotations-{title}.md`

**→ 进入 7.4 组装。**（策展模式无审查步骤，用户即质量门。）

### 7.4 共用组装：分享稿

**输出语言固定为中文。**

结构（四块）:
1. **引言**: 这篇讲什么、为什么分享（1-2 句）。
2. **心得正文**: dump → D2 整合稿；策展 → 重点摘录 + 我的批注（按保留点组织）。
3. **总结**: 关键启示（无指定长度）。
4. **推荐语**: 两版，**≤100 汉字**（社交动态）+ **≤200 汉字**（博客前言），文稿内标注用途。

通则: 全文区分原文 vs 我的话；数据/名称保持原值。
保存: `{title}/takeaways/share-{title}.md`

### 7.4b 质量审查（共用，中文成稿必经）

对 share-{title}.md 跑三道检查（可并行 subagent），任一不通过则修正后复审，最多 2 轮:
1. **翻译味儿审查**: 检出并改掉翻译腔（欧化句式、机译感），让中文读起来像母语写作。
2. **可读性审查**: 句子冗长、逻辑跳跃、结构混乱等阻断理解的问题。
3. **AI 味儿审查**: 检出并改掉 AI 写作痕迹（破折号堆砌、三段式、套话、空洞修饰等）。

报告: `{title}/takeaways/review-quality-{title}.md`

**依赖提示（实现时处理，跨 skill）**: 三道检查需对应 prompt 文件。按仓库 `docs/shared-evaluation-prompt-sync.md` 约定，优先复用已存在的共享 prompt 并保持版本同步（AI 味儿 ↔ summary/translator/hn-digest 的 `evaluate-ai-tone-prompt.md`；可读性 ↔ summary 的 reader-audit；翻译味儿 ↔ translator 若有），不另起炉灶、避免漂移。实现前先盘点已有 prompt；若 talk 的检查需求与现有 prompt 实质不同，才独立成文。

### 7.5 文件清单
