## 1. 背景

### 1.1 现状

现有 `yiyue31-translator`（v2.5.0）在**小文章（≤40KB）单 chunk 路径**上稳定有效。2026-08-27～30 用它翻译 **AI-Native SDLC Playbook（64KB / 1000 行）** 时进入多 chunk 路径，流程整体失守，最终未闭环交付。

### 1.2 本次 run 的关键事实（复盘数据）

- 64KB 原文 → **53 个碎 chunk**（20B–4.8KB，均值 ~1.2KB）
- 审校计划 = 53 chunk × 4 维度（准确性/翻译腔/AI味/可读性）= **212 份独立 subagent 报告**
- 首轮审校**整体造假**（mass-write 同秒多份、undersize、模板内容），PM 验收随之造假
- 被该 skill 自带的 `verify-pipeline.js` 终检抓住（mass-write 签名、完备性矩阵、尺寸下限全部命中）
- 真实重做 208 份审校：**~7-8 小时净执行、跨 6+ 会话段、2 个日历日**（08-29 11:02 → 08-30 07:12）
- **最终仍未闭环**：chunk 39 的 4 份报告缺失；`verify-pipeline-report.md` 停在 08-29 23:12 的 FAIL，未重跑

### 1.3 证据文件

均在 `refined-stock/AI-Native-SDLC-playbook/translation/` 下：`PM_HANDOFF.md`（问题清单）、`verify-pipeline-report.md`（终检 FAIL）、`verify-results.json`（机械校验 59 条记录）、`PROGRESS.md` / `STATUS.md` / `REVIEW_HANDOFF.md`（临场发明的 handoff，互相矛盾）、重做后的 `review-*-chunk-*.md`（真实性样本）。

### 1.4 大文档定义

**>40KB**（单条件；"分段后 chunk 数 ≥8"分支废除——旧粒度时代遗留的死条件，2026-08-30 一致性终检统一）。在此之下自动交接现有 translator。

### P1 严重类（流程设计缺陷）

| # | 问题 | 证据 |
|---|---|---|
| 5 | **chunk 碎片化**：按标题切分 + min-size 合并仅限"相邻同级别"，标题密集文档碎成 53 片，下游 O(N) 成本放大 ~8× | chunks/ 尺寸分布 |

| # | 问题 | 证据 |
|---|---|---|
| 9 | 翻译腔：欧化句式、直译痕迹（"组织已经开始使用智能体 AI"等） | PM_HANDOFF.md §3 |

### 根因（5 条，决定设计方向）

1. chunk 粒度失控 → 成本放大器
2. 审校成本 O(chunks × 维度) 与低内存串行机器不匹配，**流程物理上不可达成 → 造假成为阻力最小路径**（检测器反而成功了）
3. 断点续跑是临场发明的，不是 skill 的一等公民
4. 关卡是纪律性的，不是结构性的
5. 审校与译文无 sha 绑定

## 3. 目的（用户意图）

从与 Yiyue 的对话中提炼，按优先级排序：

1. **质量最高优先级**（2026-08-30 裁决）：准确、术语一致、无翻译腔的专业译文压倒一切——**耗时与 token 消耗让位于质量**，该加的评审加、该用 subagent 的用 subagent
2. **过程可信**：每一步真实执行、留痕、可独立核验；杜绝造假（包括 agent 自欺）
3. **跑得完且续得上**：长流程跨会话幂等续跑；**上下文溢出、/compact、OOM、关机、限流一律走同一条"断点续跑"路径**（状态纯落盘，重跑状态命令即恢复）——跑得完靠粒度+续跑机制，绝不靠砍质检
4. **成本透明而非受限**：开始时公告预估（步数/调用数/会话数），结束时对账——只记录不设限；资源异常的出口是**暂停与续跑**，不是削减质量维度
5. **完全独立**：与现有 translator 零共享——不共用脚本运行态、不共用 terms.md，各自演进，互不影响
6. **零介入（zero-touch）**：从发起（只需给原文）到交付，正常路径与异常路径**全部自动决策**——所有"需要用户拍板"的点一律默认值化（原文变更自动重翻受影响 chunk、返工超限自动升级、资源异常自动暂停+续跑），**披露不询问**：自动决策全部记入交付体检报告（REPORT.md），用户想看再看。用户介入仅剩两处：PENDING-USER 挂起的极少数必要节点（事后处理，不阻塞退出）、可选的事后亲自复核（audit 命令）。见 FR-15 与附录 A。

### 非目标

- 不承接小文章（≤40KB）——现有 translator 的领地
- 不做摘要/心得/合并等其他 skill 的活
- 不自动触发下游发布管线（交付即止，与现 translator 一致）
- 不追求"零 subagent"——准确性审校的独立性保留

## 4. 功能需求

### FR-1 大粒度分段

- 目标粒度 **8-15KB/chunk**，按标题结构切分；64KB 文档应产出 **6-8 个 chunk**（而非 53 个）
- 碎块合并**允许跨标题级别**（修掉"仅相邻同级别"限制）；code block / 表格永不被切开
- 分段器基于现有 `doc_segmenter` fork 修改

### FR-2 全维度全覆盖 QC（质量优先版）

| 层 | 执行方式 | 覆盖 | 关键点 |
|---|---|---|---|
| 机械校验 | 脚本 | 全覆盖，**每次修复后强制重跑** | fork verify-mechanical.js + 扩展（数字保真/残留英文/覆盖度下限） |
| 译前产物评审 | 独立 subagent ×1 | glossary / keep-list / special-phrases 复核 | 一条一译合规、覆盖度、双选拦截后放行 |
| 准确性 | 独立 subagent | 全覆盖 | fork evaluate-translation-prompt.md + 数字/否定词/条件句专项；与翻译**异模型**（环境不可控时记录模型 id + REPORT 披露——披露不验证，与 DESIGN 定案一致） |
| 翻译腔 | 独立 subagent | 全覆盖 | fork evaluate-translationese-prompt.md |
| AI 味 | 独立 subagent | 全覆盖 | fork evaluate-ai-tone-prompt.md |
| 可读性 | 独立 subagent | 全覆盖（含每 chunk 尾部定向关注） | fork evaluate-readability-prompt.md |
| 统稿决策 | 独立 subagent ×1 | 全稿一致性清单 | fork consistency-checklist.js 产物，只读清单下结论 |
| 终稿冷读者 | 独立 subagent ×1-2 | **全稿通读**（>30KB 分段接力，工作值 M3 校准） | 新增：以读者身份找文风断裂与明显错误，结论进 REPORT |
| 文风基准卡 | 主 agent 产物（Step 2），经译前评审复核 | 全文 | 喂给全部译者；统稿/冷读者判卷标准（2026-08-30 采纳） |

四维度**不合并、不抽样**（2026-08-30 裁决：合并与抽样是成本妥协，质量优先下撤销）。预算只做透明对账（NFR-5）**不设硬顶**。规模参考（64KB/8 chunk，**审校单元减半**后）：翻译 8 + 裁定 8 + 审校 16 半块 × 4 维 = 64 + 译前评审 1 + 统稿 1 + 冷读 2 ≈ **基线 ~88 次调用（含探针 4），数小时净执行、3-6 个会话**——耗时不是约束，断点续跑保证跑得完。

### FR-3 状态机与续跑（文件系统 = 唯一真相源）

- `progress.json` 升级为 per-chunk × per-stage 状态机，记录内容 sha
- **冷启动 = 跑一条状态命令**，输出当前矩阵 + 下一个未完成单元；禁止手写 handoff 散文（本次 6 份矛盾文档的教训）
- 状态推导逻辑 = verify-pipeline.js 重写为 **status.mjs**（状态机/resume oracle）+ **final-gate.mjs**（终检）——verify-pipeline 的文件系统取证思路保留

### FR-4 结构性关卡（不靠纪律靠机制）

- merge 步骤**只接受"最新一次机械校验 passed"的 chunk**（按 sha 匹配）
- **终检新鲜度（规格修正）**：显式定义产物集合与豁免清单（pm-review/状态文件/verify 报告自身）；固定顺序 = pm-review 先写 → 终检最后跑 → PASS 时脚本产出交付物；mtime 只作 WARN，硬判锚为内容 sha 与重执行结果
- 终检 PASS + pm-review 刷新 = 交付前置条件，是流程的**最后一个动作**

### FR-5 版本绑定与 stale 判定

- 审校报告头部记录被审译文的 sha1
- 译文在审校后变更 → 相关报告自动标记 stale，状态脚本报出，需重审或复核
- 修复译文 → 强制重跑该 chunk 机械校验（修复本身可能打破 code-block）

### FR-6 会话预算

- 启动时按 chunk 数估算总会话数并告知用户
- 每会话处理 N 个单元（默认预算可配置）后**干净退出**（配合 SessionEnd 自动 publish），不靠 OOM/上下文溢出被动中断；N 的取值同时约束**内存与主会话上下文增长**
- 每个单元（chunk × stage）幂等：中断后重入无副作用

### FR-7 异常处理矩阵（原"合法降级矩阵"，质量优先版重构）

- 资源异常（限流 / OOM / 内存紧张 / **上下文溢出**）的唯一合法出口 = **暂停 + 断点续跑**：checkpoint 后干净退出，恢复后从断点继续——**永不削减质量维度**
- 质量维度（准确性 / 翻译腔 / AI 味 / 可读性 / 冷读）**无任何跳过路径**；pm-review 合规表中不存在质量维度的 SKIPPED 合法标记
- 返工不收敛（每 chunk >3 轮）→ **升级而非降级**：换模型重翻该 chunk；仍不收敛 → **自动转 PENDING-USER 挂起**（2026-08-30 拍板：质量优先下不带病交付）——绝不静默放过
- 真正必须用户的极少数节点（如付费授权、内容违规裁量）→ **PENDING-USER 挂起态**：干净退出并附一行说明，用户处理后自动续跑——这是"零介入"的唯一合法例外
- 原则修正：让"暂停等待"永远比"造假/偷工"容易

### FR-8 与现有 translator 的分工

- 触发边界：`yiyue31-translator` description 注明"大文档（>40KB）请用 yiyue31-xl-translator"；本 skill description 明确"仅大文档"
- **零共享**：各自目录、各自脚本、各自 terms.md，互不引用
- **输出目录独立**（2026-08-30 裁决）：refined-stock 侧产物落 **`xl-translator/<title>/`**，与 `translator/`、`summary/` 等其他 skill 的输出目录完全分开；M5 时写入 CLAUDE.md 约定表，并确认 `classify()` 归类及中间产物临时名不命中任何 deliverable 模式

### FR-9 资产复用（fork 一份，此后独立演进）

一次性复制进本 skill 目录（之后不再同步）：
- `doc_segmenter`（改合并逻辑：跨级别合并、code-block 保护）
- `verify-mechanical.js`、`verify-pipeline.js`（后者扩展为状态机/resume oracle）
- 4 份 evaluate prompt（四份各自独立保留——不合并，质量优先裁决）+ 新增冷读者 prompt
- `word-counter.js`

**terms.md 独立自建**：首次从 translator 的 terms.md **一次性拷贝作种子**（2026-08-30 关闭开放问题 1：拷贝），此后不再自动同步；周期合并**推迟为人工习惯**（非机制）。

fork 的双份维护成本已记录在风险表。

### FR-15 零介入与故障模式自动对策

**原则**：附录 A 的每一条故障模式都必须落成"自动检测 → 自动对策 → 自动验证"三段式闭环，任何一条不得以"询问用户"作为对策。用户输入只有原文（可选 translation-brief，不填走默认值）。

- **默认值化**：translation-brief 缺省 = 技术读者 / 意译 / 中等注释密度 / 发布用途；原文变更自动作废并重翻受影响 chunk；返工超 3 轮自动**升级**（换模型重翻；仍不收敛转 PENDING-USER 挂起）；资源异常自动**暂停 + 断点续跑**（不削减质检）；必须用户的极少数节点转 PENDING-USER 挂起态。
- **披露不询问**：一切自动决策（升级、重翻范围、异常处置）记入 REPORT.md 与 pm-review 合规表；会话内只在干净退出时输出一行"下次说××即可继续，进度 X/Y"——这是通知，不是介入。
- **目录即验收面**：附录 A 每条对策在设计阶段须对应到具体机制（脚本/subagent/流程步），验收时按目录抽检（红队测试的植入缺陷从目录中选取）。

### FR-16 并发参数（默认 1）

- `--concurrency N` 控制 chunk 级并发，**默认 1（串行）**——本机低内存纪律下唯一安全值，亦是全局"禁止并行调度"规则的合规默认
- 仅限互不依赖的阶段（翻译/裁定/机械校验/四维审校）；统稿、冷读者、终检永远单发
- 前提改造：**边界交接包开工前从原文统一预生成**（不再依赖前 chunk 翻译产物）——消除跨 chunk 耦合与 stale 摘要隐患，串行模式同样受益
- 内存占用 ×N：本质是"用内存换日历时间"；**禁止执行 agent 自动上调**，仅用户显式设置；**N>1 并发实现推迟 v2（2026-08-30 拍板，参数位保留）**——v1 只实现串行，消灭并发共享状态问题
- 质量不变：并发只重叠独立单元，审校覆盖与预算对账不受影响

## 5. 非功能需求

| # | 需求 |
|---|---|
| NFR-1 | **资源**：在 1.87GB 内存、串行 subagent 约束下物理可达成；主 agent 不并行 fan-out（遵守全局低内存纪律） |

## 6. 验收标准（以 SDLC-playbook 为验收用例）

1. 从 `original-AI-Native-SDLC-playbook.md` 重跑全流程：chunk 数 6-8；四维度审校全覆盖（不合并/不抽样）；调用数与耗时对账进 REPORT（无硬顶）
2. `final-gate.mjs`（verify-pipeline 重写版）终检 **PASS 且新鲜**（晚于产物集合中非豁免项；mtime 软判，硬判锚 = 内容 sha + 重执行）
3. 审校报告 100% 真实（无 mass-write 签名、无 undersize、含具体引用与建议）
4. 术语一致率：抽检 20 个 glossary 条目，全文译法统一
5. P2 类译文问题（翻译腔/残留英文）抽读 3 个 chunk 无复发
6. 中断续跑演练：kill 掉中途会话 → 新会话冷启动 → 状态命令正确指向断点
7. 与现有 translator 无触发冲突（小文章仍走原 skill）
8. 红队负向测试：植入假报告 / 篡改 sha / 偷删 chunk 三场景全部被终检捕获（FAIL）
9. 中途 SessionEnd 演练：未过终检的中间产物不被 publish（临时名不命中 classify()）
10. 上下文溢出演练：主会话中途 /compact → 重跑状态命令 → 从断点正确续跑

## 7. 风险与缓解

| 风险 | 等级 | 缓解 |
|---|---|---|
