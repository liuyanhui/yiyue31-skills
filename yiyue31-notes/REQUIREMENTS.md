# yiyue31-notes 需求文档

## 1. 背景与动机

### 现状
- 已有 `yiyue31-talk` 技能：通过交互式讨论提取用户观点，生成用户视角的心得文档
- 已有 `yiyue31-summary` 技能：自动生成文章的客观总结

### 问题
两个技能各自生成独立的文档，用户需要：
1. 分别查看两个文档才能获得完整的个人学习总结
2. 没有统一的"个人学习心得"文档，整合客观内容和主观思考

### 目标
创建一个新技能 `yiyue31-notes`，将上述两个技能的输出合并为一个统一的个人学习笔记文档。

**核心定位**：合并工具（不是编排者）
- 输入：talk 和 summary 的结果文件
- 前置条件：**两个结果文件必须同时存在**

**核心使用场景：**
1. **博客发布分享**：对外发布，让读者了解文章内容并看到你的思考
2. **个人回顾**：日后复习时能快速回想起学习过程和关键收获

---

## 1.1 双目标设计分析

### 两个目标的特点对比

| 维度 | 博客发布分享 | 个人回顾 |
|------|-------------|---------|
| **读者** | 外部读者（不了解背景） | 自己（了解背景） |
| **篇幅** | 适中，不宜过长 | 可详细，方便回忆 |
| **讨论记录** | 精简或省略 | 保留，记录思考过程 |
| **重点** | 有价值的观点和结论 | 完整的学习路径 |
| **可读性** | 高，适合快速阅读 | 中，重点是信息密度 |

### 设计方案选项

**方案A：单一输出，平衡两者**
- 生成一个文档，兼顾分享和回顾
- 优点：简单，一次生成
- 缺点：可能难以同时满足两个场景的需求

**方案B：两种输出，各司其职**
- 博客版：精简、对外友好、去掉讨论细节
- 个人版：详细、保留讨论过程、完整记录
- 优点：针对性强
- 缺点：需要维护两个模板

**方案C：分层输出**
- 生成一个文档，通过 Front Matter 或标记区分部分
- 发布时可以手动选择发布哪些部分
- 优点：灵活，一次生成
- 缺点：需要手动编辑

### 推荐方案：方案B（两种输出）

建议生成两个文件：
1. `{title}/blog-post-{title}.md` - 博客发布版
2. `{title}/personal-notes-{title}.md` - 个人回顾版

## 3. 功能需求

### 3.1 核心功能
1. **合并现有输出**：将 talk 和 summary 的输出合并为一个或多个文档
2. **统一结构**：提供清晰的组织结构，区分客观内容和主观观点
3. **保持信息完整**：不丢失任何有价值的内容
4. **前置检查**：确保两个输入文件都存在

### 3.2 输入来源（必须同时存在）
- `{title}/summary/final-summary-{title}.md`（文章总结）
- `{title}/talk/user-viewpoints-{title}.md`（用户观点）
- `{title}/talk/qa-{title}.md`（讨论记录，可选但推荐）

### 3.3 前置条件检查
```
IF 两个输入文件都存在:
    继续执行合并
ELSE IF 只有 summary 存在:
    提示：请先运行 yiyue31-talk 生成用户观点
ELSE IF 只有 talk 存在:
    提示：请先运行 yiyue31-summary 生成文章总结
ELSE:
    提示：请先运行以下技能：
    1. yiyue31-summary
    2. yiyue31-talk
```

### 3.4 输出内容（待确认数量）
**方案A：两种输出**（博客版 + 个人版）
- `{title}/blog-post-{title}.md`（博客发布版）
- `{title}/notes-{title}.md`（个人回顾版）

**方案B：单一输出**
- `{title}/learning-notes-{title}.md`（统一版本）

## 4. 设计考虑

### 4.1 待解决的问题

| 问题 | 说明 | 待讨论 |
|------|------|--------|
| **执行顺序** | 是否需要协调两个技能的执行顺序？ | 🤔 理想顺序：先生成 summary，再做 takeaways |
| **重复内容** | 两个输出都有"洞察/启发"部分，如何区分？ | 🤔 文章的洞察 vs 我的思考 |
| **篇幅控制** | 合并后可能很长，如何组织？ | 🤔 是否需要精简版选项？ |
| **目录结构** | 合并后的输出放哪里？ | 🤔 新目录 vs 复用现有目录 |
| **模板选择** | 需要多少种合并模板？ | 🤔 综合版 / 精简版 / 其他？ |
| **润色处理** | 合并后是否需要 humanizer？ | 🤔 自动润色 vs 用户选择 |
| **部分完成** | 如果只有 summary 或只有 takeaways，如何处理？ | 🤔 报错警告 vs 生成部分文档 |

### 4.2 内容组织方式

#### 方式1：线性模式（Linear）
- 结构：Summary 完整展示 → Talk 完整展示
- 适合：快速阅读，先了解文章再了解观点
- 优点：简单可靠，易于实现
- 流程：
  ```
  [文章概述] → [核心内容] → [我的观点] → [总结]
  ```

#### 方式2：交织模式（Interleaved）
- 结构：按章节 Summary → Talk 对应观点穿插
- 适合：深度阅读，边看文章边思考
- 优点：紧密关联，深度整合
- 缺点：实现复杂，需要章节匹配
- 流程：
  ```
  [章节1 Summary] → [我对章节1的看法]
  → [章节2 Summary] → [我对章节2的看法]
  → ...
  → [综合总结]
  ```

**实现策略**：
- 第一版：实现线性模式（MVP）
- 第二版：添加交织模式支持

## 7. 架构决策记录

### 决策：保持 skill 独立

**日期**：2026-04-29

**决策**：将 `yiyue31-notes` 作为独立 skill，不集成到 talk 中。

**理由**：
1. **单一职责原则**：每个 skill 只做一件事
2. **可组合性**：三个 skill 可以灵活组合使用
3. **可维护性**：独立 skill 更容易测试和维护
4. **最小依赖**：避免 talk 依赖 summary

**用户便利优化**：
- 在 talk 完成时提示用户是否合并
- 在 summary 完成时提示是否继续生成用户观点

## 9. 方案总结

### 方案A：简化版（线性分层结构）

**特点**：
- 快速了解层：概述 + 观点概览
- 详细内容层：文章内容 + 观点详情（线性展示）
- 总结层：合并的收获与启发

**优势**：
- 实现简单，快速可用
- 逻辑清晰，易于理解
- 维护成本低

**适用场景**：
- 第一版快速验证
- 简单文章类型
- 观点和章节对应关系不强

### 方案B：优化版（分层交织结构）

**特点**：
- 快速了解层：概述 + 观点概览
- 详细内容层：按章节交织展示内容+观点
- 总结层：合并的收获与启发

**优势**：
- 内容紧密关联
- 阅读体验流畅
- 符合边读边思考的习惯

**适用场景**：
- 正式使用，追求最佳体验
- 复杂文章类型
- 观点和章节有明确对应关系

**实施前提**：
- 需要 viewpoint-mapping 文件
- 需要章节匹配逻辑
- 维护成本较高
