# Article Rewriting and Takeaways Generation Skill

此技能用于将别人的文章改写成自己的心得体会，生成结构清晰、可发表的markdown文档。

## workflow

严格按照以下步骤执行：

### Step 1: 格式化输入文档

首先将用户输入的内容转换为统一的Markdown文档。

**输入来源处理：**

1. **URL**：- **URL输入**：优先使用本地已安装的skills，如：下载文章、转换文章、抓取网页、操作网页、查看网页等skills。其次，使用 `wget` 或 `curl` 打开网页并下载文章内容。
2. **文件路径**：如果用户提供的是文件路径（.md, .txt, .pdf, .docx等），读取文件内容
3. **粘贴内容**：如果用户直接粘贴了文本内容，直接使用

**保存原始文档：**

创建目录结构并保存原始内容：
```
{文章标题}/raw-{文章标题}.md
```

文章标题从原文中提取，或使用简短的描述性名称。

### Step 2: 分析原文

阅读并分析原文，提取以下信息：

- 文章的核心主题和主旨
- 文章结构（章节划分）
- 按章节分析关键观点和论据
- 文章类型（技术文章、管理心得、经验分享、学术论文等）
- 原文的篇幅和复杂度
- **提取实体名词**：识别关键名词、概念、人物、组件、技术术语等，分析它们之间的关系。

**保存分析结果：**

```
{文章标题}/analysis-raw-{文章标题}.md
```

### Step 3: 生成实体关系图（如果不需要可以跳过，但是要告知用户）

根据Step 2提取的实体，生成Mermaid代码。数据缺失或者关系不确定时，请用户协助。

**支持的可视化类型：**

- **思维导图（mindmap）**：展示概念的层级关系
- **实体关系图（ER）**：展示实体之间的关联
- **流程图**：展示流程或步骤

**输出格式：**

```markdown
# [文章标题] - 实体关系图

## 核心实体
[列出文章中的关键名词、概念、人物、组件等]

## 思维导图
\`\`\`mermaid
mindmap
  root((主题))
    子主题1
      概念A
      概念B
    子主题2
      概念C
\`\`\`

## 实体关系图
\`\`\`mermaid
erDiagram
    实体A ||--o{ 实体B : 关系
\`\`\`
```

**保存位置：**

```
{文章标题}/entities-{文章标题}.md
```

**用户确认**：向用户展示实体关系图，确认提取的实体是否准确、关系是否完整。等待用户确认后再继续。

### Step 4: 交互式讨论与记录

本步骤采用**交互式讨论**模式，AI和用户通过对话深入探讨文章内容，类似于导师与学生、同事之间的讨论。

**讨论规则：**

1. **AI问AI（自问自答）**：针对文章中的难点，AI生成问题并记录答案
   - "文章中提到的[概念X]具体是指什么？"
   - "[技术Y]与[技术Z]有什么区别？"
   - "作者为什么选择[方案A]而不是[方案B]？"

2. **AI与用户交互讨论**：
   - AI可以发起提问，用户回答后，用户可以追问，AI继续回应
   - 用户可以主动提问，AI回答后可以追问用户的理解
   - 往复对话，深入探讨
   - 用户决定何时结束讨论

**示例对话流程：**

```
AI: 你对文章中的[概念X]有什么理解？
用户: 我觉得它是...，但我不太确定[细节Y]
AI: 你的理解基本正确。关于[细节Y]，文章中提到...
用户: 那如果应用到实际场景中，会怎么样？
AI: 好问题！根据文章的观点...
```

**讨论主题建议：**

- 对概念的理解和澄清
- 与用户经验的联系
- 观点的启发和思考
- 实际应用的探讨

**保存讨论记录：**

```
{文章标题}/qa-{文章标题}.md
```

格式示例：
```markdown
# 交互式讨论记录

## AI问AI（自问自答，帮助理解）
1. Q: [问题] 
   A: [AI根据文章内容的回答]

2. Q: [问题]
   A: [AI根据文章内容的回答]

## AI与用户讨论

### 讨论主题1：[主题]
**AI**: [问题或观点]
**用户**: [回答或疑问]
**AI**: [回应或追问]
**用户**: [进一步思考]

### 讨论主题2：[主题]
**用户**: [主动提问]
**AI**: [回答]
**AI**: [追问用户的理解]
**用户**: [回应]
```

**同时收集改写所需信息：**

在讨论过程中或结束后，确认以下信息：
1. **改写目的**是什么？
2. **目标读者**是谁？
3. **重点侧重**于什么？
4. **篇幅要求**？
5. **个人背景**（用于生成更贴合的"我的心得"）
5. **你的角色/身份**？

### Step 5: 选择输入类型和输出风格

读取 `templates/input-types.md` 和 `templates/output-styles.md`。

**AI推荐**：根据文章类型，推荐输入类型+输出风格组合。

示例：
- 原文是技术案例分析 → 推荐 `TECH-CASE + FIRST` 或 `TECH-CASE + REFLECT`
- 原文是管理经验分享 → 推荐 `MGMT-EXP + PRACTICE` 或 `MGMT-EXP + REFLECT`

**用户确认或指定**：用户可以接受AI推荐，或指定自己的组合。

**记录选择**：更新 `templates/history.md`

### Step 6: 生成心得草稿

根据分析结果、实体关系图和用户选择，生成心得草稿。

**输出格式：**

```markdown
# [文章标题] - 心得草稿

## 文章要点
- 核心观点1
- 核心观点2
- 核心观点3

## 我的理解
[对文章内容的个人理解]

## 心得体会
[个人的收获和感悟]

## 可应用的经验
[可以应用到实际工作中的经验点]
```

**保存位置：**

```
{文章标题}/takeaways-{文章标题}.md
```

**用户确认**：向用户展示草稿，等待用户确认或修改。只有用户确认后，才继续生成最终文章。

### Step 7: 生成最终文章

基于确认后的心得草稿，生成最终改写文章。

**输出格式：**

```markdown
# [新标题]

## 要点速览
- 要点1
- 要点2
- 要点3

## 总结
[文章的核心内容和主旨]

## 心得体会
[个人的理解和收获，根据选择的风格调整语气]

## 可吸取的经验
[具体的经验点和行动建议]
```

**保存位置：**

```
{文章标题}/rewritten-{文章标题}.md
```

**改写原则：**

1. **保持核心信息准确**：不歪曲原文的核心观点和事实
2. **融入个人理解**：将原文内容转化为自己的语言和理解
3. **结构清晰**：使用明确的章节划分，便于阅读
4. **可发表标准**：语言流畅、逻辑清晰、格式规范
5. **符合用户意图**：根据用户选择的目的、读者和风格进行调整

### Step 8: 总结和确认

完成改写后，向用户总结：
- 原文保存位置
- 分析结果保存位置
- 实体关系图保存位置
- 提问记录保存位置
- 心得草稿保存位置
- 最终改写文章保存位置
- 改写的主要变化和调整
- 询问是否需要进一步调整

## 输出文件汇总

每次任务生成的文件：

| 文件 | 说明 | 是否需要用户确认 |
|------|------|-----------------|
| raw-{title}.md | 原始文档 | 否 |
| analysis-raw-{title}.md | 分析结果 | 否 |
| entities-{title}.md | 实体关系图 | **是** |
| qa-{title}.md | 提问记录 | 否 |
| takeaways-{title}.md | 心得草稿 | **是** |
| rewritten-{title}.md | 最终文章 | 否 |

## 输出示例

**输入类型**：TECH-CASE（技术案例分析）
**输出风格**：FIRST（第一人称）+ REFLECT（反思总结）

```markdown
# 从微服务架构中学到的架构设计原则

## 要点速览
- 单一职责原则在服务拆分中的应用
- 服务间通信的利弊权衡
- 数据一致性问题的解决方案
- 容错和弹性设计的重要性

## 总结
本文讨论了微服务架构的核心设计原则，包括服务拆分策略、通信模式、数据管理和容错机制等方面。

## 心得体会
在阅读这篇文章的过程中，我深刻认识到微服务架构不仅仅是技术选型问题，更是业务建模和团队组织的问题。从我的经验来看，成功的服务拆分需要深入理解业务边界，而不仅仅是技术层面的分离。

回顾我之前参与的项目，我们在服务拆分时过于关注技术层面，导致后期维护成本增加。这篇文章让我反思：应该先从业务能力和团队组织角度来思考服务边界。

## 可吸取的经验
1. 在拆分服务时，优先考虑业务边界而非技术边界
2. 服务间通信要考虑延迟和失败场景
3. 数据一致性要采用最终一致性模型
4. 要建立完善的监控和日志系统
```
