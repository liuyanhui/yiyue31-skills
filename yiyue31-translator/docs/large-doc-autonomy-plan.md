- 3/7（compaction-in-pi、loop-engineering、the-new-rules）：完整四维真报告（2.2-9.5KB），跨文件 MD5 查重零重复

- 多 chunk 路径从 >40KB 就激活，但压力致死区约在 10+ chunks

## 6. 决策记录（2026-08-24 用户拍板）

**问题**：大文档翻译频率低（观察值 1/8），是否值得为此实施 P0？

**用户回答**：≥100KB 长文档翻译"基本结束"——一次性需求，今后一年最多一两次，翻不翻无所谓。

### 6.1 S5 设计要点（verify-pipeline.js）

**定位**：任务结束时程序生成"任务报告"（步骤×产物×状态矩阵 + 红旗清单 + 终判），验证过程真实性，不依赖 LLM 自我汇报。

**七类确定性检查**：

1. **完备性矩阵**（跳过检测）：按 manifest + 步骤清单枚举应存在产物（每 chunk 译文、每维度报告、glossary/keep-list/合并文件），缺失即 FAIL
2. **占位符检测**：报告标题含未替换的 `Chunk XX`、`{title}` 等
3. **同维度查重**：同维度报告 MD5 相同或尺寸异常聚集（如 14×220B）
4. **批量写入签名**：同维度 ≥5 份报告 mtime 落在同一分钟窗口（物理上不可能是独立 subagent 审校）
5. **时序一致性**：报告 mtime 必须晚于对应译文 mtime
6. **脚本产物核验**：verify-mechanical 每次运行把退出码追加落盘 `verify-results.json`；终检核对"全部 exit 0"的声明与落盘记录（杀"声称已跑"式伪证）
7. **尺寸下限随 chunk 大小缩放**：报告字节数 ≥ f(chunk 尺寸)

**输出**：markdown 任务报告 + 落盘 `verify-report.json`；退出码 0/1。终判三态：PASS / FAIL / WARN-SKIPPED（与 S4 咬合：pm-review 合规表已披露的 `⏭️ SKIPPED(reason)` 报 WARN=合法降级，未披露的缺失报 FAIL=作弊）。

**诚实边界**（勿过度承诺）：形态检查抓得住本案两代失败（模板伪造、静默跳过），抓不住"尺寸正常的水货报告"和"精心定制的下一代伪造"；作用是把伪造成本抬到高于诚实工作，不是消灭。**检查器由 agent 运行的汇报本身不可信**（harness-v2 的 PM 连"脚本已跑"都伪造过），最终锚点是用户交付时跑一条命令：`node verify-pipeline.js <title>/translation`；远期可挂进 refined-stock publish 做 pre-publish 门禁（范围外，§7）。

**否决清单及理由**（勿在冷启动时重新论证）：

- P0-1 切分修复：真 bug 但触发频率趋近零（多 chunk 路径今后基本不激活）。留档，再触发再修。
- P0-2 合并脚本化 / P0-3 状态派生 / P0-4 自修复+一行回传：全部服务于多 chunk 报告量与上下文压力，单 chunk 主场景无此压力。
- P0-5 verify-reports：初轮以"大文档报告压力"为由否决；后经 abc-legal 证据（小规模同样触发跳过）+ 用户对 LLM 不确定性的关切，以"过程真实性、全场景"的新论据复活为 S5（二轮批准）。其大文档专用语义（报告瘦身配套等）仍不实施。
- P1-9 砍维度 / P1-10 批处理：大文档压力的答案，需求不存在则不修。
- 环境类根因（VPS 内存、跨设备搬运半成品）：使用习惯问题，偶发大文档时按 S2 提示规避，不改 skill。

**偶发大文档时的操作指引**（写给未来自己）：在本机正常内存环境跑、不分设备搬运半成品状态、接受少量介入；或手工分两三批发起；产出如需发布，发布前人工抽查审校报告尺寸是否异常（<500 字节的"通过"报告即为空壳信号）。
